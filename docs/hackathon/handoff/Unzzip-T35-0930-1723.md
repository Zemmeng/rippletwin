# Unzzip · T35 · 2026-09-30 17:23

*Archived from the hackathon (29 Sep – 1 Oct 2026). Translated from the original Chinese; superseded details are kept as they were.*

Outside the detailed window (La Trobe × Swanston), the "vector" basemap used to contain only real buildings + real roads, and it did not look like a real map. This change replaces it with a **real OSM vector map**: water, green space, land use and railways, fetched at build time from OpenFreeMap's OpenMapTiles vector tiles and decoded into a local file. At runtime the web page still fetches only same-origin files.

**Why it is wired this way** (rather than connecting to a tile service at runtime)

- The repo has a hard constraint: `test_web.py` asserts negatively that the page's `fetch()` calls may only hit same-origin `/engine/ /roads/ /params/ /api/`, and the only external domain allowed is Google Fonts. The privacy reason for [3] is also written in the test comments. Connecting to a third-party tile service at runtime would overturn both the assertion and its rationale.
- Fetching at build time follows exactly the same path as `network.json` / `buildings.json` / `flows.json`: the data source is recorded in the file (`tile_source`, `sources`), and the live page makes no outbound requests.
- The tile source is OpenFreeMap: the public instance is free, needs no key, explicitly says there is "no limit on the number of requests", and officially offers a full-planet offline download, so fetching a few tiles at build time is a supported use. **Passed over**: Maptoolkit's Community License explicitly forbids offline tile generation / bulk extraction; MapTiler and Stadia need keys; MapLibre's official demo tiles only have country borders.
- z14, 6 tiles: the CITY layer cache is 1.6 px per page unit (≈ 0.625 m/px), and z14's geometric precision is about 0.47 m per unit, which is enough; one zoom level higher doubles the size with no visible difference.

```
$ python3 apps/web/build.py && python3 apps/web/tests/test_web.py | tail -1
63 passed, 0 failed
$ bash apps/roads/test.sh | tail -1     # rerun again under [5] below
```

I also rendered the decoded result as a separate PNG and checked it by eye (the Yarra, the Flagstaff / Carlton / Fitzroy Gardens, the many tracks of the Flinders St yards and the tram line on each street all line up), and ran an A/B test in Chromium at 1440×900 with `vectormap.json` blocked / not blocked: in both the light and dark themes, the area outside the detailed window went from "a field of grey grid" to a real map "with a river, parks, rail corridors and scattered small green spaces", with no regressions.

**Pitfalls hit (worth recording)**

- `python3 -m http.server 4175 -d apps/web/public` is the README's "page only" way to start; that root has no `/roads/`, so `vectormap.json` and `buildings.json` both return 404 → the page falls back to the fallback layer **by design**, but the console shows only one `console.info` line. That fooled me at first; I thought the change had not taken effect. This is now written into `apps/web/README.md`.
- After changing `src/`, always run `python3 apps/web/build.py`: the first test in `test_web.py` checks that `public/index.html` matches `src/`, so it goes red if you do not rebuild.
- MVT's `Layer.name/keys/values` must be identified by field number (3/4 = length-delimited); packed fields (`Feature.tags`, `Feature.geometry`) must first be decoded into a varint array and then zigzag-decoded; a polygon starts a new ring at every MoveTo, rather than being split at ClosePath.

## 3. For the lead

- **Cross-module change**: this spans `apps/roads` (@louisxie316-dotcom) and `apps/web` (@unicornnnnnny), plus two lead-only files (section 2 above). Following the convention, the branch is named `Unzzip/web/T35-osm-vectormap` (the main change is in web), and the push used `ALLOW_CROSS=1`; I did **not** add the `cross-module` label to the PR myself. Per the repo rules I am waiting for you to confirm and add it, which re-runs CI.
- Two things for you to decide:
  1. Which **layers** the vector basemap uses: it currently draws only water / green space / land use / railways and does **not** use the roads in the tiles (that layer keeps using the real network from `network.json`, because it is the same data as the links the engine computes on, so two sets of lines can never drift apart). If you want "the roads from the tiles too", adding `transportation` to the data file takes only a few lines, but the CITY layer would then be misaligned with the engine's lines by a few metres.
  2. The detailed window (La Trobe × Swanston) is **not replaced**: its coordinates are stretched piecewise (`geoToWorld`, ×1.85 north of La Trobe), so real tiles will not line up. Replacing it would first require changing the detailed window's projection to a uniform scale, which touches the simulation, the weather rasters and four test files; not advisable the night before.
- Data snapshot: `vectormap.json` uses the 2026-09-27 OpenMapTiles snapshot (recorded in `tile_source`). It does not need refetching after the freeze; if it really must be refetched, run `python3 apps/roads/tools/fetch_vectormap.py --refresh`, and the diff will only be the OSM edits other people made in these few days.
